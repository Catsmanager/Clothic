경로 기준: 앱 파일의 짧은 경로와 앱 명령은 `frontend/` 기준이다. `docs/`, `supabase/`, `HARNESS/`, `.github/`는 저장소 루트 기준이다.
작성일: 2026-11-10\
상태: 학습·설계 참고 문서. 이 문서의 "Supabase 인증과 데이터를 유지한다"는 전제는 첫 전환 단계에 한정된다. 2026-11-13에 Supabase 독립을 결정했으며 근거는 [ADR-004](../architecture/ADR.md#adr-004-supabase에서-독립해-로그인과-데이터-저장을-직접-운영한다)다. 실제 기능별 진행 상태는 루트 [plan.md](../../plan.md)에서 확인한다.\
기준: `release/app-store-1.1.1`의 `73c9863`\
계획서 작업 브랜치: `docs/spring-boot-migration-plan`\
상위 작업: [GitHub 이슈 #175](https://github.com/Catsmanager/Clothic/issues/175)

## 1. 지금 가장 먼저 할 일

**기존 Supabase 인증과 데이터를 유지하면서, 로그인 사용자의 옷 목록 조회 하나를 Spring Boot로 옮긴다.**

먼저 아래 응답 계약을 기준으로 작은 서버를 실행하고, 인증 → 데이터 조회 → 앱 연결 순서로 범위를 넓힌다. 전체 기능을 한 번에 다시 만들지 않는다.

첫 구현 단위는 **Java 21 기반 `backend/` 프로젝트 생성과 상태 확인 요청 성공**이다. 데이터베이스와 앱은 이 단계에서 연결하지 않는다. 실제 착수·완료 여부는 [plan.md](../../plan.md)의 F-01에서 관리한다.

## 2. Supabase 연결은 어떻게 되는가

| 구분 | 현재 확인한 코드 | 첫 기능 전환 후 목표 |
| --- | --- | --- |
| 로그인·세션 | 앱 → Supabase Auth | 그대로 유지 |
| 옷 목록 조회 | 앱 → Supabase Data API → PostgreSQL `items` | 앱 → Spring Boot → 기존 Supabase PostgreSQL `items` |
| 사용자 식별 | Supabase 세션과 데이터베이스의 행 수준 보안(Row Level Security, RLS) 정책 | Spring Boot가 토큰을 검증해 사용자를 식별하고, 해당 사용자 조건으로 조회 |
| 코디·알림 등 다른 기능 | 앱 → Supabase | 첫 기능 전환 동안 유지 |
| 데이터 저장 위치 | Supabase PostgreSQL을 대상으로 하는 코드 | 그대로 유지. 기존 데이터 복사·삭제 없음 |

**Spring Boot 서버 도입과 Supabase 서비스 전체 제거는 서로 다른 작업이다.** 첫 단계에서는 Supabase 계정이나 테이블을 삭제하지 않는다. 데이터베이스·인증 서비스까지 옮길지는 조회 전환 이후 별도 결정한다.

JPA 연결은 Supabase Data API를 거치는 연결과 다르다. 앱의 접근 토큰이 JDBC 연결에 자동으로 전달되어 `auth.uid()`가 설정된다고 가정하면 안 된다. JDBC는 Java Database Connectivity, JPA는 Jakarta Persistence API를 뜻한다.

백엔드 데이터 접근은 Spring Data JPA로 학습한다. Supabase Data API를 사용자 토큰과 함께 중계하는 방식도 가능하지만, 이번 계획에서는 Java 객체·테이블 매핑과 저장소 조회까지 직접 다루기 위해 JPA 방식을 선택한다. 연결 권한과 RLS의 실제 동작은 4단계에서 확인한다.

| 테이블·정책 | [스키마 마이그레이션](../../supabase/migrations/20260613000100_normalize_app_schema_and_rls.sql), 17~25·88~102행 | `items.user_id`와 `auth.uid() = user_id` 정책 정의 |

현재 조회에는 `.eq('user_id', ...)` 조건이 없다. 저장소에 정의된 RLS 정책을 전제로 하는 구조다. 운영 데이터베이스에 정책이 실제 적용되었는지는 아직 확인하지 않았다.

또한 현재 옷장 화면은 소유한 모든 옷의 단순 목록이 아니다. 기본 카탈로그와 사용자 아이템을 합치고, 코디 기록·계절 조건으로 계산한다. 첫 API에는 **사용자별 `items` 행만** 반환하고, 기존 카탈로그 결합과 화면 계산은 유지한다. 이후 `main`에 있는 카탈로그/소유 아이템 분리 변경은 이번 전환과 섞지 않고 별도 비교한다.

## 4. 첫 API의 계약 — 제안

API는 Application Programming Interface, HTTP는 Hypertext Transfer Protocol을 뜻한다. 아래 주소와 응답 형식은 새로 구현할 계약이며 현재 존재하는 API가 아니다.

```http
GET /api/items
Authorization: Bearer <Supabase 사용자 접근 토큰>
```

- 사용자 ID를 요청 쿼리나 본문으로 받지 않는다.
- 서버가 검증한 토큰의 사용자 식별값 `sub`에서 사용자 ID를 얻는다.
- 해당 `user_id`의 행만 조회하고 `created_at` 내림차순으로 반환한다.
- 같은 생성 시각끼리의 순서는 현재 계약에 없으므로 비교 검증에서 별도 순서를 가정하지 않는다.
- 응답은 현재 `UserItem[]`에 대응하는 배열로 정한다. 엔티티 객체 자체를 반환하지 않는다.

```json
[
  {
    "id": "11111111-1111-4111-8111-111111111111",
    "userId": "22222222-2222-4222-8222-222222222222",
    "name": "테스트 셔츠",
    "category": "top",
    "imagePath": "",
    "color": "#ffffff",
    "styleTags": ["casual"],
    "createdAt": "2026-11-10T00:00:00Z"
  }
]
```

위 값은 설명용 예시이며 실제 사용자 데이터가 아니다. 필드는 [현재 UserItem 타입](../../frontend/stores/itemStore.ts)의 15~23행을 기준으로 한다. 날짜는 시간대가 포함된 형식으로 반환하고, 비교 시 같은 시각인지 확인한다.

| 상황 | 목표 응답 |
| --- | --- |
| 유효한 인증 + 아이템 있음 | `200`과 본인 아이템 배열 |
| 유효한 인증 + 아이템 없음 | `200`과 `[]` |
| 토큰 없음·위조·만료·다른 발급자 | `401`, 목록 반환 없음 |
| 허용하지 않은 `userId` 쿼리 파라미터 | `400`, 요청값으로 조회 대상을 바꾸지 않음 |
| 데이터베이스 조회 실패 | `500`, 내부 SQL·접속 정보가 없는 오류 응답 |

기존 `mapRow()`의 카테고리·스타일 태그 정리 규칙도 보존한다. 서버의 응답 변환 계층에서 같은 허용값을 적용하고, 허용되지 않는 카테고리 행은 응답에서 제외한다. 기본 카탈로그를 데이터베이스에 자동 등록하지 않는다.

## 5. 학습과 구현 순서

각 단계에서 필요한 개념만 익히고 적용한다. 완료 기준을 확인한 뒤 다음 단계로 넘어간다. 구현 단위마다 #175에 결과를 남기고, 작업 브랜치와 PR(Pull Request)로 변경을 분리한다.

### 1단계 — 현재 동작과 계약을 고정한다

- 이 문서의 첫 API 계약을 구현 기준으로 확정한다.
- 기존 조회 결과·카탈로그 결합·화면 계산의 책임을 구분한다.
- 테스트용 사용자 A·B와 사용자별 아이템, 빈 목록, 잘못된 분류 데이터를 정의한다.
- 운영 환경의 실제 스키마·추가 컬럼·RLS·접속 역할은 미확인 항목으로 기록한다.

학습: HTTP 요청·응답, 상태 코드, 서버와 데이터베이스의 역할.\
완료 기준: “어떤 요청에 누구의 어떤 데이터가 반환되는가”를 코드 없이 설명할 수 있다.

### 2단계 — Spring Boot 서버를 실행한다

- `feat/spring-boot-bootstrap` 작업 브랜치를 만든다.
- Spring Initializr로 `backend/`에 Java 21·Maven 기반 프로젝트를 만든다.
- 생성 시점의 Java 21 호환 정식 Spring Boot 버전을 확인하고 빌드 파일에 고정한다. Spring Framework 버전은 Boot가 관리하도록 한다.
- 첫 의존성은 Spring Web과 기본 테스트 지원으로 제한한다. 보안은 3단계, JPA·PostgreSQL 드라이버는 4단계에서 추가한다.
- Maven Wrapper를 포함해 전역 Maven 설치 없이 실행할 수 있게 한다.
- 데이터베이스를 사용하지 않는 `GET /api/health`를 만들고 `{"status":"ok"}` 응답을 확인한다.

학습: Java 클래스·record, Spring의 의존성 주입(Dependency Injection, DI), Controller, Boot 자동 설정.\
완료 기준: `backend/`에서 `./mvnw test`가 통과하고 `./mvnw spring-boot:run`으로 실행한 서버가 상태 확인 요청에 `200`을 반환한다. 기존 앱은 변경하지 않는다.

현재 Java Development Kit(JDK) 21.0.13은 설치되어 있고 `java`·`javac` 실행을 확인했다. 전역 `mvn`·`gradle`, `docker`·`psql` 실행 파일은 현재 셸 경로에서 찾지 못했다. 설치되지 않았다고 단정하지 않으며, 필요한 실행 도구는 각 단계에서 확인한다.

### 3단계 — Supabase 사용자 토큰을 검증한다

- Spring Security와 OAuth 2.0 Resource Server 지원을 추가한다.
- 개발 환경의 실제 토큰 발급자·대상·서명 알고리즘을 확인한다. 토큰과 비밀키 원문은 문서·로그에 남기지 않는다.
- 비대칭 서명이면 JSON Web Key Set(JWKS) 공개키로 JSON Web Token(JWT)을 검증한다. 레거시 대칭 서명이면 JWKS 방식이 된다고 가정하지 않고 검증 방식을 따로 결정한다. 운영 서명 키 변경은 이 단계에 포함하지 않는다.
- 서명·발급자·만료·적용 대상 검증 후 유효한 사용자 식별값만 서비스에 전달한다. 토큰을 단순 디코딩한 값을 신뢰하지 않는다.
- `/api/items`는 인증 필수로, `/api/health`만 공개 상태 확인 경로로 지정한다.
- 유효한 인증과 실패 인증을 테스트한다. 웹 실습을 지원할 때만 개발 웹 주소의 교차 출처 리소스 공유(Cross-Origin Resource Sharing, CORS)를 설정한다.

학습: 인증과 인가의 차이, 보안 필터, 토큰 검증, 서버가 신뢰할 수 있는 사용자 ID.\
완료 기준: 토큰이 없거나 유효하지 않으면 아이템 서비스·저장소 조회에 도달하지 않는다. 실제 Supabase 토큰 연동 확인과 테스트용 모의 인증 검증을 구분해 기록한다.

### 4단계 — 사용자별 아이템을 조회한다

- 운영과 분리된 PostgreSQL 테스트 데이터베이스를 준비한다. 실행 도구 설치·개발 데이터베이스 준비를 별도 환경 작업으로 기록한다.
- Spring Data JPA와 PostgreSQL 드라이버를 추가하고 `Item`·저장소·서비스·응답 객체를 구성한다.
- `id`·`user_id`의 UUID(Universally Unique Identifier), `style_tags` 배열, `created_at` 시간대 매핑을 실제 PostgreSQL에서 검증한다.
- 조회 조건은 개념적으로 `WHERE user_id = :인증된사용자ID ORDER BY created_at DESC`로 고정한다. 전체 조회 후 메모리에서 사용자를 거르지 않는다.
- 사용자 A·B가 각각 자기 행만 조회하는지 저장소부터 HTTP 응답까지 확인한다.
- 기존 Supabase PostgreSQL 연결 전, 접속 역할·권한·RLS와 인증 문맥 전달 여부를 확인한다. 백엔드 전용 읽기 권한 설계를 기록하고 관리자 계정을 기본 접속값으로 사용하지 않는다.
- ORM(Object-Relational Mapping)의 자동 테이블 생성·수정을 끈다. 기존 스키마 연결은 `ddl-auto=validate` 등 검증만 수행하도록 한다. 테스트 스키마는 별도 스크립트로 준비한다.
- 접속 문자열·비밀번호는 서버 환경변수로 받는다. Expo 공개 환경변수나 Git 저장소에 넣지 않는다.

학습: Entity·Repository·Service, 객체와 테이블 매핑, 데이터 전송 객체(Data Transfer Object, DTO), 읽기 트랜잭션.\
완료 기준: 실제 PostgreSQL에서 본인 데이터만 반환하고, 빈 결과·잘못된 데이터·조회 실패를 구분한다. 메모리 데이터베이스 테스트만 통과한 상태를 PostgreSQL 연동 완료로 표시하지 않는다.

RLS가 유지돼 있더라도 접속 역할에 따라 적용 방식이 달라질 수 있다. 반대로 JWT 문맥이 없는 일반 연결에서는 정책 때문에 조회가 거부될 수 있다. 실제 권한·정책을 확인하기 전에는 어느 쪽도 단정하지 않는다. 서버의 사용자별 조회 조건은 항상 유지한다.

### 5단계 — 앱의 옷 조회 경로 하나를 연결한다

- 기존 Supabase 인증 클라이언트에서 현재 접근 토큰을 얻어 새 서버 요청에 전달한다.
- `lib/itemsApi.ts` 같은 요청 모듈을 만들고, `stores/itemStore.ts`의 `fetchItems()` 내부 조회 경로만 바꾼다.
- 서버 주소를 앱 실행 환경에 맞춰 설정한다. 실기기의 `localhost`가 개발 컴퓨터를 가리킨다고 가정하지 않는다.
- `items`·`loading`·`loaded`·`error`, `reset()`과 늦게 도착한 응답 차단 규칙을 유지한다.
- 요청 시간 제한과 예외 처리를 넣고, 실패했을 때 로딩 종료·오류·재시도가 이어지는지 확인한다.
- 서버 응답을 실행 시점에도 검사한다. TypeScript 타입 단언만으로 응답이 올바르다고 처리하지 않는다.
- 기본 카탈로그 결합, 코디 조회, 통계·잠자는 옷장 계산은 현재 동작을 유지한다.
- 개발 설정으로 기존 직접 조회와 새 서버 조회를 명시적으로 선택해 비교한다. 인증 실패를 숨기는 자동 우회는 넣지 않는다.

학습: 인증된 HTTP 요청, 비동기 실패 처리, 프론트엔드·백엔드 계약, 계정 전환 중 상태 관리.\
완료 기준: 같은 사용자·데이터에서 기존 경로와 새 경로의 아이템 결과가 같고, 로그아웃·계정 전환·서버 오류에서도 이전 사용자 데이터가 다시 나타나지 않는다.

### 6단계 — 검증 기록을 남기고 다음 범위를 정한다

- 서버 테스트와 앱의 `npm run check`를 실행한다. 서버 검증을 기존 앱 검사 통과로 대체하지 않는다.
- 실제 개발 환경에서 인증 → 조회 → 화면 표시 → 실패·재시도 → 재로그인을 확인한다.
- CI(Continuous Integration, 지속적 통합)에 서버 검사 단계를 추가한다.
- 실행 방법·환경변수 이름·인증 및 DB 접근 구조·검증 결과·미검증 항목을 문서화한다.
- 기존 직접 조회로 되돌리는 절차를 기록하고 개발 환경에서 확인한다.
- 이후 기능은 코디 조회 → 코디 저장·수정·삭제 → 프로필·알림·계정 삭제 순서의 후보로 검토한다. 구현·검증 단위는 다시 나눈다.
- 개발 환경 검증 후 배포 구성과 운영 전환을 별도 작업으로 구체화한다. 운영 전환 전에는 첫 조회 기능 마이그레이션이 운영까지 완료됐다고 표시하지 않는다.

학습: 단위·통합 검증의 차이, 회귀 검증, 실행 기록과 복귀 절차.\
완료 기준: 첫 조회 기능의 개발 환경 결과와 설명 가능한 코드가 있으며, 운영 전환에 남은 작업이 명확하다.

## 6. 완료 판단에 반드시 포함할 사례

| 사례 | 확인할 결과 |

| 새 경로와 기존 경로를 비교 | 사용자별 필드·아이템 집합·날짜 의미·정렬 규칙 일치 |

## 9. 공부하는 방식

1. 작업 전 해당 단계의 요청·입력·반환값·실패 조건을 짧게 적는다.
2. Java 문법은 현재 코드에 필요한 클래스·record·인터페이스·생성자·컬렉션·예외부터 익힌다.
3. AI에는 한 단계의 기능·파일 범위와 완료 기준을 주고 제한된 변경만 요청한다.
4. 생성된 코드의 요청 → 인증 → 사용자 조건 → 조회 → 응답 흐름을 직접 추적한다.
5. 정상·실패 사례를 실행하고, 설명할 수 없는 부분을 검토·수정한 뒤 기록한다.

권장 기록 형식: `이번 요청 / 내가 예상한 흐름 / 실제 코드 / 검증 결과 / 아직 모르는 점`.
