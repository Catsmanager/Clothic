# Avatar Asset Scale Roadmap

## 목표

Clothic은 최종 출시 전까지는 앱에 포함된 기본 옷 에셋으로 안정적인 코디 경험을 제공한다.
출시 후 앱이 커지고 사용자 수가 늘어나면, 사용자가 직접 옷을 저장하고 관리할 수 있는 구조로 확장한다.

이 문서는 아바타/의상 에셋이 앱을 무겁게 만들지 않도록 단계별 기준을 정리한다.

## 기본 원칙

- 원본 제작 파일과 앱 번들용 파일을 분리한다.
- 앱에 포함되는 이미지는 실제 화면 표시 크기에 맞게 최적화한다.
- 캐릭터 착용용 레이어와 목록/선택 화면용 썸네일을 분리한다.
- 출시 전에는 단순한 로컬 번들 구조를 유지한다.
- 출시 후 사용자 업로드/저장은 서버 스토리지로 확장한다.

## 현재 상태

- 기본 아바타: `assets/avatar/base/base_female_01.png`
- 의상 레이어 위치: `assets/avatar/{category}/...png`
- 카탈로그: `constants/itemCatalog.ts`
- 정적 이미지 매핑: `lib/avatarAssets.ts`
- 등록 파이프라인:

```bash
npm run avatar:add -- ...
```

- 검증 파이프라인:

```bash
npm run avatar:check
```

현재 파이프라인은 의상 레이어를 base 아바타와 같은 크기로 맞춘다.
이 방식은 정렬이 쉽지만, 옷 수가 많아지면 앱 용량이 커질 수 있다.

## Phase 1: 출시 전 MVP

목표: 앱에 기본 의상 세트를 내장하고, 기능 완성도를 우선한다.

권장 범위:

- 기본 아바타 1종
- 상의 10개 내외
- 하의 8개 내외
- 신발 6개 내외
- 가방 5개 내외
- 액세서리 3개 내외

이 단계에서는 모든 기본 에셋을 앱 번들에 포함해도 된다.
총 의상 수가 30-50개 정도라면 관리 가능하다.

주의할 점:

- 원본 고해상도 이미지를 그대로 대량 번들링하지 않는다.
- 출시 전 대량 제작에 들어가기 전에 앱용 표준 해상도를 확정한다.
- 옷 이미지는 반드시 base 위에 정확히 맞춘 전체 투명 캔버스로 제작한다.

## Phase 1 권장 해상도

현재 고해상도 base는 선명하지만, 모든 옷을 같은 고해상도로 넣으면 앱이 무거워질 수 있다.

권장 구조:

```text
작업 원본: 887x1774 또는 그 이상
앱 착용 레이어: 512x1024
앱 썸네일: 256x256
```

출시 전에는 파이프라인을 다음 구조로 바꾸는 것이 좋다.

```text
assets/source/avatar/...      작업 원본, 앱 번들 제외 후보
assets/avatar/...             앱 착용 레이어
assets/avatar-thumbs/...      앱 썸네일
```

MVP에서는 썸네일 생성을 나중으로 미루고, 먼저 착용 레이어만 안정화해도 된다.
다만 옷 수가 늘어나는 시점에는 썸네일 분리가 필요하다.

## Phase 2: 출시 직전 최적화

목표: 앱 번들 크기와 런타임 메모리 사용을 점검한다.

체크리스트:

- 모든 의상 PNG가 같은 캔버스 기준으로 정렬되어 있는지 확인
- 앱 착용 레이어 해상도 확정
- 선택 목록에서 큰 레이어 이미지를 직접 쓰는지 확인
- 필요 시 별도 썸네일 생성
- PNG 압축 도구 도입 검토
- 앱 설치 파일 크기 확인
- 저사양 기기에서 스크롤/아바타 렌더링 확인

압축 도구 후보:

```text
pngquant
oxipng
sharp
```

최종 출시 전에는 `npm run avatar:check`에 다음 검사를 추가하는 것이 좋다.

- 파일 크기 상한
- 앱 레이어 해상도
- 썸네일 존재 여부
- 카탈로그 등록 누락 여부

## Phase 3: 출시 후 기본 의상 확장

목표: 기본 의상 수를 늘리되 앱 업데이트 비용을 관리한다.

전략:

- 시즌별 기본 의상은 앱 업데이트로 추가
- 대량 의상팩은 원격 다운로드 구조 검토
- 앱에 항상 필요한 기본 의상만 번들에 포함
- 사용 빈도가 낮은 의상은 서버에서 받아오는 구조로 분리

가능한 구조:

```text
내장 기본 의상: 앱 번들
추가 의상팩: Supabase Storage 또는 CDN
사용자 업로드 의상: 사용자별 Storage
```

이 단계에서는 `itemCatalog.ts`를 정적 배열만으로 유지하기 어렵다.
원격 카탈로그 테이블 또는 JSON manifest가 필요해진다.

## Phase 4: 사용자 저장/업로드 확장

목표: 사용자가 직접 옷을 저장하고 코디에 활용할 수 있게 한다.

사용자 아이템 구조:

```text
items 테이블
- id
- user_id
- name
- category
- color
- style_tags
- image_path
- thumbnail_path
- created_at
```

이미지 저장 구조:

```text
Supabase Storage
users/{userId}/items/{itemId}/layer.png
users/{userId}/items/{itemId}/thumb.png
```

필요 기능:

- 이미지 업로드
- 배경 제거 또는 투명 PNG 가이드
- 카테고리 선택
- 색상/스타일 태그 입력
- 썸네일 생성
- 착용 레이어 정렬 확인
- 사용자별 RLS 정책

초기 사용자 업로드는 완전 자동 정렬보다 반자동 흐름이 현실적이다.
예를 들어 사용자가 옷을 올린 뒤, 화면에서 크기/위치를 조정하고 저장하게 할 수 있다.

## 사용자 업로드 정렬 방식

자동으로 모든 옷을 몸에 맞추는 것은 어렵다.
초기 버전에서는 다음 방식이 현실적이다.

1. 사용자가 옷 PNG를 업로드한다.
2. 앱이 base 위에 옷을 올려 보여준다.
3. 사용자가 위치/크기 슬라이더로 맞춘다.
4. 보정값을 저장한다.
5. 코디 렌더링 시 보정값을 적용한다.

저장할 보정값 예시:

```json
{
  "x": 0,
  "y": -0.08,
  "scale": 0.86
}
```

이 구조를 쓰면 모든 사용자 업로드 이미지를 새 PNG로 다시 굽지 않아도 된다.

## 권장 의사결정

최종 출시 전까지는 다음 결정을 먼저 확정한다.

1. 앱 착용 레이어 표준 해상도
2. 썸네일 분리 여부
3. 원본 파일 보관 위치
4. PNG 압축 도구 도입 여부
5. 사용자 업로드를 출시 범위에 포함할지, 출시 후 기능으로 둘지

현재 목표를 기준으로는 다음을 추천한다.

```text
출시 전:
- 기본 의상 내장
- 사용자 업로드 제외
- 앱 레이어/카탈로그 파이프라인 안정화

출시 후:
- 사용자 저장 기능 추가
- Supabase Storage 기반 이미지 관리
- 사용자별 정렬 보정값 저장
```

## 다음 작업 후보

- `avatar:add`가 원본 보관, 앱 레이어 생성, 썸네일 생성을 함께 하도록 확장
- 앱용 표준 해상도를 `512x1024`로 확정할지 검토
- `CatalogItem`에 `thumbnailPath` 필드 추가
- `lib/avatarAssets.ts`를 수동 매핑에서 자동 생성 파일로 분리
- 사용자 업로드용 DB/Storage 설계 문서 작성
