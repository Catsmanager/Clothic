# Clothic Task Workflow

사용자가 Clothic 작업을 실행하라고 하면 저장소 파일을 바꾸기 전에 최소 완료 단위를 정하고 GitHub 원격 작업 브랜치를 확인한다. 문서·계획서·스킬 파일 생성도 파일 변경 작업에 포함한다.

## 작업을 나누는 기준

- 한 브랜치는 독립적으로 검증하고 검토할 수 있는 한 가지 결과를 만든다. 파일 수를 기준으로 쪼개지 않는다.
- 문서 이동과 그 문서를 가리키는 링크 수정은 같은 작업이다. 문서 폴더 정리와 새로운 작업 절차 스킬은 서로 다른 작업이다.
- 같은 완료 기준을 위한 후속 수정은 기존 작업 브랜치를 이어 쓴다. 별개 목표가 추가되면 새 작업으로 분리한다.
- 설명만 요청하거나 코드를 읽어 달라는 요청에는 브랜치·이슈·파일을 만들지 않는다. 계획을 Markdown 파일로 만들어 달라는 요청은 작업으로 취급한다.

## 파일 변경 전 필수 절차

1. 현재 저장소·원격 주소·브랜치·HEAD·작업 디렉터리 상태를 확인한다. 필요한 작업 지침과 관련 코드·문서를 읽는다.
2. 한 작업의 목표, 수정 범위, 완료 기준, 기준 브랜치와 커밋을 짧게 정한다. 해당 범위를 추적하는 GitHub 이슈를 연결한다. 적합한 기존 이슈가 없으면 작업별 이슈를 만든다.
3. 기존 변경은 보존한다. 다른 작업의 변경이 섞여 있으면 별도 작업 트리를 쓰거나 기존 작업 브랜치에 먼저 정리한다. 사용자 변경을 임의로 스테이징·폐기·덮어쓰기하지 않는다.
4. 기준 브랜치를 확인하고 로컬 작업 브랜치를 만든다. 사용자가 지정한 배포 기준이나 상위 작업을 임의로 main 최신 상태로 바꾸지 않는다.
5. **아직 저장소 파일을 수정하지 않은 상태에서 GitHub에 같은 브랜치를 생성한다.** GitHub 도구를 사용하거나 현재 작업 브랜치를 즉시 push하고 원격 추적을 연결한다.
6. GitHub ref 또는 git ls-remote로 원격 브랜치가 실제 존재하고 시작 커밋이 로컬 HEAD와 같은지 확인한다. 로컬 브랜치만 있거나 push 명령을 시작한 상태는 확인 완료가 아니다.
7. 이슈·기준 SHA·로컬 브랜치·원격 ref 확인 결과를 기록한 뒤 해당 작업의 파일 변경을 시작한다.

브랜치 이름은 docs/이슈번호-목적, feat/이슈번호-목적, fix/이슈번호-목적, chore/이슈번호-목적처럼 작업을 구분할 수 있게 정한다. 기존 브랜치를 이어 쓸 때는 이슈·범위·원격 HEAD를 다시 확인하고 진행한다. 진행 중인 작업에는 정상적인 로컬 미푸시 커밋이 있을 수 있으므로 이를 강제 덮어쓰기 사유로 삼지 않는다.

예를 들어 Git 명령을 사용할 때는 다음 흐름을 따른다. placeholder는 실제 확인한 값으로 바꾼다.

```bash
git switch -c docs/177-organize-documents <verified-base>
git push --set-upstream origin HEAD
git rev-parse HEAD
git ls-remote --heads origin refs/heads/docs/177-organize-documents
```

GitHub 연결 도구가 필요한 기능이나 쓰기 권한을 제공하지 못하면 인증된 Git 또는 GitHub CLI를 사용한다. 네트워크·권한 오류는 환경의 승인·재시도 절차를 따른다. 허용된 방법으로도 원격 브랜치 생성을 확인할 수 없으면 파일 변경을 시작하지 말고 실패 원인을 보고한다. 조사와 임시 위치의 요청 초안 준비는 계속할 수 있다.

## 통합과 버전 지정 릴리스

버전·배포·GitHub Actions를 다루는 작업에서는 [개발·릴리스 가이드](../../../docs/operations/CICD.md)를 읽는다. 일반 작업에서 릴리스 전체 절차를 불필요하게 실행하지 않는다.

- 기본 개발 흐름은 작업 브랜치 → PR → 모든 PR의 CI 검증 → main 통합이다. 독립 작업은 확인한 통합 기준에서 시작하고, 미병합 작업에 의존할 때만 상위 브랜치를 기준으로 한다. 사용자가 고정한 배포 기준은 우선한다.
- main 통합과 실제 앱 배포를 구분한다. main이 항상 현재 App Store 공개 버전이라고 보고하지 않는다.
- 작업·커밋마다 앱 버전을 올리지 않는다. 배포할 변경이 모였을 때 별도 버전 준비 PR에서 앱·패키지·잠금 파일 버전을 맞춘다.
- 앱은 app-vX.Y.Z 태그를 사용한다. 서버는 구현 후 backend-vX.Y.Z 등 별도 규칙으로 관리하며, 서버 변경을 이유로 앱 버전을 기계적으로 올리지 않는다.
- 릴리스 태그는 main에 포함된 검증한 커밋을 가리켜야 한다. 기존 공개 태그를 다른 커밋으로 옮기거나 덮어쓰지 않는다.
- node scripts/check-release.mjs versions로 파일 간 버전을 확인하고, 앱 릴리스에서는 해당 태그까지 지정해 검사한다.
- iOS 자동 릴리스는 정식 GitHub Release 게시를 기준으로 한다. 수동 실행도 기존 버전 태그를 지정하고 빌드·제출 범위를 구분한다.
- 빌드 결과의 앱 버전·소스 커밋·완료 상태를 확인한 뒤 그 빌드 ID로 제출한다. 최신 빌드라는 이유만으로 --latest를 사용하지 않는다.
- 규칙·workflow 수정 요청을 실제 태그 push, Release 게시, EAS 빌드·스토어 제출 요청으로 확대 해석하지 않는다. 사용자에게 해당 실행을 요청받은 경우에 진행한다.
- CI 실행과 GitHub 보호 설정을 구분한다. 브랜치 보호·환경 승인자가 실제 설정돼 있는지 확인하지 않고 강제된다고 보고하지 않는다.
- workflow 코드 검증, main 병합 여부, 실제 빌드·TestFlight 처리·App Store 공개를 각각 확인한 범위로 보고한다.

## 작업과 완료

- 범위를 넓히는 새 목표는 같은 브랜치에 끼워 넣지 않는다. 별도 브랜치로 나누되 필요한 선행 작업을 명시한다.
- 변경에 맞는 검증을 수행한다. 문서 이동은 파일 보존·상대 링크·문서 참조를 확인하고, 실행 코드 변경은 해당 동작을 검증한다.
- 저장소 규칙에 따라 TODO.md와 LOG.md를 갱신한다. 완료한 구현, 실제 실행한 검증, 미확인 상태를 구분한다.
- 현재 작업의 파일만 명시적으로 스테이징해 커밋하고 해당 원격 작업 브랜치에 push한다. 이미 완료한 단계를 중복 수행하지 않는다.
- 현재 저장소 지침은 작업 완료 후 PR 생성을 요구한다. 해당 작업의 PR을 만들거나 갱신하고 이슈·변경 결과·검증 내용을 연결한다. 사용자가 명시적으로 로컬 작업만 요청했다면 그 지시를 우선한다.
- 상위 작업이 아직 병합되지 않았다면 PR의 기준을 상위 브랜치로 설정하고 의존하는 PR을 연결해 현재 작업의 차이만 검토할 수 있게 한다.
- 사용자 요청이나 저장소 지침이 이미 허용한 일반 작업을 다시 승인받으려고 멈추지 않는다. 이 스킬은 보호 규칙 우회, 강제 push, 임의 브랜치 삭제, PR 병합 또는 배포 권한을 추가하지 않는다.
- 최종 보고에는 작업별 브랜치와 PR 링크, 검증 결과, 남은 미확인 사항을 간단히 적는다.
